# 架構審查紀錄

## 已修正
| # | 問題 | 影響 | 修正 |
|---|---|---|---|
| 1 | `prebuild` 在建置時改寫 `vercel.json` | Vercel 的 redirects/headers 很可能在建置前就決定，當次部署不一定套用新轉址（需實測） | 改為本機 `npm run sync` 產生並 commit；`integrations/validate-data.mjs` 在每次 `astro build` 前檢查同步，不同步就中止建置 |
| 2 | 資料驗證只掛在 npm `prebuild` | 部署平台直接跑 `astro build` 會繞過 | 驗證移進 Astro integration，跟著框架走 |
| 3 | 缺少商品圖片欄位與規範 | 圖片無寬高造成 CLS；無 alt 影響無障礙與 SEO | 新增 `image`（檔案+alt），放 `src/assets/products/` 用 Astro `<Image>`；驗證與稽核都檢查 |
| 4 | robots.txt `Disallow: /go/` 與 `X-Robots-Tag: noindex` 並用，文件稱「兩者都要有」 | 被 robots 擋掉的爬蟲看不到 header，兩者有交集限制 | 文件改為如實說明；保留 Disallow（原始規格），若日後 `/go/` 被索引再調整 |
| 5 | 每日連結檢查含 `--follow` | 從 GitHub 機房 IP 打賣場常被限流，每天都是「無法判斷」，成為噪音 | CI 只檢查自己的網域；`--follow` 改為每週在本機手動執行 |
| 6 | workflow 把 `vars.SITE_URL` 直接插進 shell 指令 | 變數內容若被污染有注入風險 | 改用 `env` 傳遞 |
| 7 | 週流程（價格紀錄、vercel.json）會改檔，但 AI 規則是「不主動 commit」 | 流程斷在最後一步，部署的仍是舊資料 | 附錄明確寫「commit & push 部署」，並要求提醒使用者 |
| 8 | 轉址數量沒有上限意識 | 商品多了可能碰到 Vercel 設定上限 | 超過 1000 條時警告，請查官方文件並考慮 Edge Middleware（上限數字不憑記憶斷言） |
| 9 | 範圍混在一起 | 旅遊、新通路提前建置會拖慢家電站上線 | 預設只啟用蝦皮+酷澎；旅遊範本移到 `templates/`，Step 14 在 Step 10 上線後才做 |

## 已知限制（接受）
- 促銷到期與年份在「建置時」判斷；每日重建之間（約 00:00–04:00）可能短暫顯示已過期促銷。
- 價格不是即時價（靜態站），頁面標示更新日期與「以賣場頁面為準」。
- 賣場頁面的商品層（缺貨、價格劇變）無法可靠自動偵測，靠每週人工抽測與聯盟後台轉換率。
- 價格「自動取得」取決於各平台是否提供官方資料介面與條款是否允許；本套件不內建爬蟲，預設 manual，資料來源接口已備好。
- 內容與社群刻意保留人工核准，不做無人值守發布。
- 點擊追蹤精度取決於選用的方案（beacon 會被部分廣告攔截器擋掉），所以對帳看「比率變化」而非絕對值。

## 需實測（不憑記憶）
- Vercel：redirect 是否附加原 query、`/go/` headers 是否出現在 redirect 回應、vercel.json 數量上限、建置中產生的 vercel.json 是否生效。
- 蝦皮／酷澎：連結網域與聯盟參數名稱、App 喚醒行為、條款是否允許轉址。
- Threads 內嵌瀏覽器的 UA 字串。

## 第三輪：與另一份架構（Next.js + SSR + API 轉址）的比較與取捨
**採用**：情境落地頁 `/{品類}/for/{情境}`（鎖定高購買意圖搜尋）、以缺點區／規格區可見時間判斷購買意圖（取代整頁停留＋捲動）、蝦皮與酷澎雙 CTA（副標只由資料算出）、抽屜事件紀錄、自適應篩選、酷澎官方 API provider（使用者已確認存在）。
**不採用**：Next.js／SSR／Supabase／API Route 轉址（50 款常青商品靜態輸出即可，邊緣轉址比函式更快、零維運）；「307 才能喚醒 App」（無依據，仍需真機實測）；沒有資料支持的文案（「現省 $X」「次低價」「明天到貨」）；「資訊型關鍵字完全不做」（改為吸收進商品 FAQ 與少量買前指南）。
**待確認（需實測／使用者提供）**：酷澎 API 文件與驗證方式（簽章或 token）、蝦皮是否有官方資料介面、兩平台聯盟後台是否支援子追蹤參數（`sub_id`）、App 喚醒行為、5 秒門檻的實際成效（看抽屜事件資料）。
